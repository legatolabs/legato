# Request-to-verified-file comparison

Each OS receives twelve fresh full-document requests of eight dependent updates. Four use exact developer-registered command forms; four contain six registered and two unregistered lines; four use entirely unregistered phrasing. Input data, wording and initial document are identical for every paired arm. The worker receives the textual request lines and the authorized application surface. A separate controller retains the expected commands and grades the ordered write journal and every value in the final file.

Compare seven configurations in balanced-by-randomization order within each request: the default baseline, tuned baseline and candidate each with eight serial model calls; tuned baseline and candidate each with one whole-request model call; and tuned baseline and candidate each with registered commands plus one model call for any unresolved lines. All model calls use Qwen2.5-3B-Instruct Q4_K_M, on the runner's CPU, greedy with a fixed seed, with no prompt-cache reuse requested. The runner verifies the model and executable archive hashes and warms the model before any timed task. This is a developer integration for one scope. The same routing and model are available to every SDK comparison.

Raw wall time includes planning, actions, receipt checks, a 350 ms delay and an independent durable-file and write-journal grade. Setup is excluded. Wrong completions, missing writes and timeouts remain in the results. Compare correctness first, all-attempt latency with failures identified, and time ratios on pairs where both produced the correct final result. Report the current SDK with the same faster policy as a control. Three input profiles are deliberately equally represented; the distribution is not production telemetry.
